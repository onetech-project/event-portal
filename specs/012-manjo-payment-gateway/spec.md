## Clarifications

### Session 2026-08-10

Supplied by the requester without prompting:

- **Outbound call**: `POST {base}/v1/manjo/transaction/incoming`, `Content-Type: application/json`, `Accept: application/json`. Development base is `http://localhost:10327`.
- **Gateway credential travels in the request body**, not in an authorization header: `ac.cr` is an object of `client_id` and `client_secret`. The merchant account number (`ac.an`) is absent from the sample and is therefore treated as optional.
- **Method payload** (`mp`) is omitted entirely for QRIS; `m` is `0` (QR).
- **Amount** (`a`) is sent as a bare JSON number, not a string.
- **Payment page design** (Figma `32:1366` waiting state, `203:1157` paid state) drives the guest-facing requirements in User Story 5: a QRIS-standard printed frame around the code, a countdown banner, an order summary with fee breakdown, a "How to pay with QRIS" step list, and a primary action that is disabled and reads "Waiting for payment…" until the payment confirms, then becomes "Get a ticket". The design contains **no** manual "check payment status" control.
- **The QR session response now carries its own expiry**, `mr.qr_ea`, as an offset-bearing timestamp (`2026-08-10T10:26:46+07:00`). This supersedes the earlier assumption that the gateway returned no deadline and that the system had to compute one.
- **Version trap**: the contract module version pinned in the backend build when this was written defines the QR response as `qr_r` and `qr_u` only — no `qr_ea`. Decoding into that older shape discards the expiry with no error raised, producing a working code beside a deadline the gateway never agreed to. A version publishing the field has since been released and the dependency must be advanced to it before FR-009 can hold. The published field is a timestamp type rather than a string, so the parse happens at the contract boundary — which removes one failure mode and introduces another (FR-009b).
- **Inbound callback**, from the gateway's own dispatch code: `POST {our_host}/v1.0/callback/exec`, `Content-Type: application/json`, `Accept: application/json`, `Accept-Language: en`. The gateway waits **5 seconds** for a response, retries up to **3 times** with a **10-second** wait between attempts, and treats **any status other than 200** as a failure worth retrying. It reads only the status code; the response body is not interpreted.

Answered during clarification:

- Q: How will the Manjo gateway prove that a request arriving at our callback endpoint genuinely came from it? → A: The gateway sends a bearer auth token. This project issues its own API key and authenticates a callback by comparing the presented token against it.
- Q: Does the gateway constrain the `ri` reference to a UUID, or will it accept any string we choose? → A: Any string is accepted, so the order number stays as the reference. The reference is capped at 25 characters.
- Q: If a callback is lost for good, how should the system find out that an order was actually paid? → A: There is no status query to fall back on. Notifications are the only source of payment truth, and staff reconcile a lost one through a new admin screen, confirming it against the gateway's own dashboard. *Superseded below: the gateway can redeliver the notification, so no staff assertion is needed and the screen does not perform one.*
- Q: Besides the endpoint URL, do the `client_id`/`client_secret` pair and the callback API key also belong in the database? → A: At the time, no — the database was to hold the URL only. *Superseded below: nothing goes in the database.* The finding that survives is that the credential pair is vestigial — the gateway validates that it is present but attaches no privilege to it.
- Q: Should the QRIS frame's merchant name, registration number, and terminal label be read out of the QR payload, or rendered as fixed branding? → A: Fixed branding for now, hardcoded. Deriving them from the payload is recorded as a deferred item under Assumptions. *Superseded by spec 020: the frame shows none of the three, so there is nothing left to derive and the deferred item is withdrawn.*

Also supplied by the requester:

- **Amount composition**: the subtotal is the ticket lines; tax is a percentage of that subtotal; the total payable is subtotal + tax + service fee. The total payable is what goes to the gateway as the amount. This confirms the behaviour already in place rather than changing it — the existing fee model computes percentage fees against the subtotal and flat fees as-is, and already sends the order total. The design's figures agree: 105,000 subtotal, 11,550 at 11%, 1,200 flat, 117,750 total.

- Q: Should the mid-window code refresh be kept? → A: No. One order yields one code, valid for one window, and the window is the expiry the gateway returns. The refresh endpoint, the per-attempt reference suffix and the stripping that matched it back, the re-issue counter and its log marker, and the client refresh timer are all withdrawn.
- Q: If the gateway returns an expiry noticeably further out than expected, should the system still adopt it as the order's deadline? → A: Yes, always, whatever its length — and raise an operational signal when it differs materially from the configured expectation.
- Q: Does the gateway support redelivering a notification on request? → A: **Yes.** Manjo has a resend-callback function, invoked **per transaction**, returning the order id and the status. This directly contradicts the earlier researched assumption of "no dead-letter path and no manual redelivery" — that was inferred from the gateway's automatic retry code, which describes only how it retries by itself and says nothing about what an operator can trigger. The assumption is withdrawn wherever it appears.
- Q: What is the reconciliation surface actually for, and should this system ever issue tickets on a person's word? → A: **Never.** The resolution is a business process that happens outside this app: the customer gives ops proof of payment, ops approves, ops tops up the ticket quota if the seats have since been sold, and ops then asks the gateway to resend the notification. The redelivered notification settles the order through the ordinary path. This system's part is to hold the order under its number so ops can look it up, and to settle it when the gateway says so. The gateway stays the single source of payment truth and there is exactly one code path that turns a payment into tickets.
- Q: When the redelivered notification arrives and the ticket type no longer has enough quota to cover the order, what should happen? → A: Do not update the status. Answer **HTTP 200** carrying an error saying the tickets are not available, so the gateway does not retry a notification that would fail again identically. The order stays expired until ops adds quota and asks for another resend. Settling proceeds only when the quota covers the order's full hold — a partial settle is not an outcome.
- Q: Should the gateway address live in the database, as originally asked? → A: No — reversed after consideration. Configuration stays in the environment, the way it already works. The database holds no gateway configuration at all, and the existing provider-named variables are renamed so they are not tied to the provider being replaced:

  | Existing | Becomes | Carries |
  | --- | --- | --- |
  | `MIDTRANS_SERVER_KEY` | `PG_SERVER_KEY` | gateway credential (secret half) |
  | `MIDTRANS_CLIENT_KEY` | `PG_CLIENT_KEY` | gateway credential (identifier half) |
  | `MIDTRANS_BASE_URL` | `PG_BASE_URL` | gateway base address — now required |
  | `MIDTRANS_IS_PRODUCTION` | *removed* | — |
  | `QR_REFRESH_AFTER` | *removed* | — |
  | `PAYMENT_EXPIRY` + `PAYMENT_WINDOW` | one value | payment window (FR-030) |

  One further variable has no predecessor and must be added: a key for authenticating inbound callbacks (FR-012). The previous provider signed its notifications in the body, so there was nothing to configure.

- Q: If the call that opens a payment session fails on a timeout or a network error, should the system retry before telling the guest checkout failed? → A: Yes — a bounded retry reusing the same reference, rather than surfacing a transient blip as a failed checkout.
- Q: What does the gateway do with a repeated reference on the session-open call? → A: It rejects it with a duplicate-reference error when a code was already created for that reference. A second session can therefore never exist for one reference, which makes a retry safe to attempt — but the error carries no code, so a retry that meets it cannot recover the payload the lost response held.
- Q: The expiry field's type changed at the contract boundary from text to a timestamp — what follows? → A: The parse moves to the contract boundary, so preserving the instant is handled there rather than by us. Two consequences: an absent value arrives as a far-past timestamp rather than as nothing, which must still be treated as the missing case; and a malformed value now risks failing the decode of the whole response, which must not be allowed to deny the guest an otherwise-valid code (FR-009e).
- Q: Is a vendor SDK being dropped in favour of plain HTTP? → A: There is no SDK to drop — none was ever used. The existing integration already speaks the provider's HTTP interface directly, with the endpoint and the HTTP client both injectable so the request shape, the response parsing, and the authentication check can be exercised without a network. What is removed is the previous provider's adapter, not a dependency. The replacement keeps the same shape.
- Q: Should the base address be required outright, or selected from built-in sandbox and production addresses? → A: Required outright, and the environment selector is dropped rather than renamed. No gateway hostname is compiled into the build; the address is the whole answer.

- Q: Which fields does the session request actually require? → A: Six — reference, amount, currency, method, merchant account with credential, and remark. The requested expiry is no longer sent at all; the gateway applies and reports its own.
- Q: When a callback reports a contradicting outcome for an order that is already paid — a rejection or cancellation arriving after the completion — what should happen? → A: The order stays paid and nothing is reversed automatically. The contradiction raises an operational signal (routine repeats stay quiet) and is recorded on the order's own record. *The original answer said the order would be "flagged in the staff reconciliation view"; with the worklist withdrawn (FR-022h) the signal and the per-order record carry it instead.*
- Q: With interval polling removed, what should the payment page do when the live stream cannot deliver — refused at the per-address cap, unsupported by the browser, or silently buffered by a proxy? → A: Stop polling while the stream is healthy, and fall back to periodic reads only while it is not — with a liveness watchdog that declares the stream dead when no frame or keep-alive arrives within twice the keep-alive interval, so silent buffering is caught too.

### Session 2026-08-11

Triggered by an observed defect on the confirmation screen's ticket-email resend: the first press sent no mail and wrote no log, the second press was refused as rate-limited, and the button then stayed refused for the rest of the page's life. The resend endpoint itself predates this feature (spec 008 FR-022), but the confirmation screen that carries it is built here, and the cooldown it needs is specified below.

- Q: How should the guest's screen learn how many seconds remain before a resend is allowed again? → A: The server states the wait. The rate-limited response body carries a `retry_after_seconds` field and the accepted response carries one too, so the countdown starts on a successful send rather than only on a refusal. The screen never computes the wait from its own clock or from a hardcoded window.
- Q: What should happen to a resend request whose body yields no order number — malformed, wrongly encoded, or missing the field? → A: Refuse it with a validation error before the limiter runs, touching no bucket and counting nothing. An unreadable body says nothing about which orders exist, so the enumeration silence does not apply to it; that silence still covers an order number that is well-formed but unknown. The shared bucket for unkeyable requests is removed rather than rescoped.
- Q: Should the server log every resend attempt, including the ones it answers with deliberate silence? → A: Yes — every attempt is logged with the outcome it actually had, while the answer to the caller stays identical across all of them. The identical-answer rule governs what the caller learns, not what the operator can see, and an outcome that is invisible in the logs cannot be told apart from a press that never happened.
- Q: Should an attempt that sends no email — unknown order, unpayable order, or a send that failed on our side — still spend the guest's cooldown? → A: Yes. Every attempt that gets past the body check spends it, whatever the outcome. The endpoint takes no authentication, so what needs capping is the work each attempt causes rather than only the mail it produces; counting deliveries alone would leave order-number probing unlimited. It also keeps the returned seconds meaning exactly one thing, which is what the countdown depends on.
- Q: After a reload, or in a second tab, should the button be armed immediately or should the page remember the cooldown it was already counting? → A: Nothing is remembered. A fresh page arms the button, and the first press either sends or returns the seconds still to wait — which the countdown then runs from. The cooldown lives in the server's memory and does not survive a restart, so a deadline held in the browser could outlast the limit it describes and make a guest wait for nothing; the refused press costs one request and always resolves to the truth. At zero the button re-arms by itself.

Triggered separately, by the observation that the callback endpoint answers a successful notification with no body at all — while the one path that does answer with a body (the FR-019c refusal) answers outside the envelope the rest of the system speaks. The endpoint currently has three response shapes across its paths.

- Q: What JSON shape should the callback endpoint's answer take? → A: The `{code, message, data}` envelope every other endpoint in this system uses. The empty 200 and the bare FR-019c object are both replaced by it, so the endpoint speaks one shape rather than one per path. The gateway itself reads only the status code, so the body serves the substitute gateway of FR-008a, the operator reading a captured response, and the tests that assert what a notification did.
- Q: Should the acknowledgement report what the notification did to the order, or only that it was received? → A: Only that it was received — `data` is null. What a notification did is already recorded durably (FR-018) and already readable per order (FR-022c), so a body naming the outcome would be a second, transient account of something the system is obliged to keep anyway, and one that could drift from the record it duplicates. The body's job is to exist, parse, and say the notification was taken; the record is where the effect is read.
- Q: An unknown order reference answered `{"code":200000,"message":"Success"}` — a notification that matched nothing reported success. Should such outcomes carry an error? → A: Yes, and not only that one. Every outcome that raises an operational signal names itself in the envelope's code (FR-012g): unknown reference, non-deposit, unrecognised status, contradiction of a paid order, and a completion for a gateway-cancelled order. The rule is the signal, not whether the order moved — if it is worth telling a human, the caller is told too. This narrows the previous answer rather than reversing it: uniformity still governs the uneventful outcomes, where a duplicate retry is the normal case and flagging it would bury the five that matter. The status stays 200 throughout, so the code remains the only discriminator.
- Q: With `data` null on every acknowledgement, what tells the FR-019c refusal apart — it leaves on the same 200 status line? → A: The envelope's code. The refusal carries a registered sub-code in the 200 band, `200001`, paired with the `TICKETS_UNAVAILABLE` machine-readable code, rather than the ordinary `200000`. The numeric scheme is status × 1000 + sub-code and no 200-band sub-code was taken, so this says "not a success" without an envelope code whose leading digits contradict the status line. The refusal keeps its shortfall detail in `data` — the one exception to the null rule, because an operator sizing a quota top-up needs the figure.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Guest pays with a Manjo-issued QRIS code (Priority: P1)

A guest completes checkout for an event. Instead of the code being obtained from the previous payment provider, the system asks the Manjo gateway to open a payment session for the order and receives a QRIS payload back. The guest sees the same on-site payment page they see today — order summary, scannable QR code, amount due, and a countdown — and scans it with any Indonesian banking or e-wallet app. Nothing in the guest's experience signals that the provider behind the code has changed.

**Why this priority**: Without a code issued by the new gateway there is no payment at all. Every other part of this migration depends on a session being opened successfully, and this is the slice that makes the switch real.

**Independent Test**: Complete a checkout against a Manjo gateway (or a stand-in that speaks the same contract) and confirm the payment page renders a scannable QRIS code, the correct amount, and a countdown — while no request whatsoever reaches the previous provider.

**Acceptance Scenarios**:

1. **Given** a guest who has just completed checkout, **When** the order is created, **Then** a payment session is opened with the Manjo gateway carrying the order's reference, total amount, currency, payment method, merchant account and credential, and a human-readable remark — and no requested expiry — and the guest lands on the order payment page.
2. **Given** the gateway answers successfully with a QRIS payload, **When** the payment page loads, **Then** it shows a scannable code rendered from that payload, the amount due, and a countdown to the payment deadline.
3. **Given** the gateway answers successfully, **When** the response is stored, **Then** the gateway's own external reference for the transaction is recorded against the order so support can trace it later.
4. **Given** the gateway answers with a failure, **When** checkout is attempted, **Then** the guest is shown an actionable error, the order remains unpaid, its reserved quota remains held, and no partially-created payment state is left behind.
5. **Given** the gateway is unreachable or does not answer in time, **When** checkout is attempted, **Then** the guest is shown an actionable error and can retry without losing their order or its quota hold.
6. **Given** the gateway answers successfully but with an empty QRIS payload, **When** the response is processed, **Then** it is treated as a failed session rather than shown to the guest as an unscannable code.
7. **Given** an order that already has a payment session, **When** anything attempts to open another one for it, **Then** it is refused — one order yields one code, valid for one window.
8. **Given** a successful session, **When** the deadline is set, **Then** it is the expiry the gateway returned, so the code stays scannable for exactly as long as the guest is given to pay.

### User Story 2 - Payment confirmation arrives on the gateway callback and completes the order (Priority: P1)

The guest pays in their banking app. The Manjo gateway notifies the system on a dedicated callback endpoint. The system recognises the order by the reference it originally sent, marks it paid, issues the tickets, and sends them — and the guest's still-open payment page switches to a paid confirmation on its own.

**Why this priority**: An issued code that never confirms is a dead end. This is what turns money received into tickets delivered, and it ships in the same MVP slice as User Story 1.

**Independent Test**: With a payment page open on an unpaid order, deliver an authenticated "completed" notification for that order's reference to the callback endpoint and confirm the order becomes paid, tickets are issued exactly once, the confirmation email is dispatched, and the open page updates itself without a manual reload.

**Acceptance Scenarios**:

1. **Given** an unpaid order with an open payment session, **When** an authenticated notification reporting a completed payment arrives for its reference, **Then** the order becomes paid, its tickets are issued, and the confirmation is dispatched.
2. **Given** the same notification, **When** it is received, **Then** it is acknowledged immediately, before ticket issuance, email delivery, or any other post-payment work runs.
3. **Given** an order that is already paid, **When** a second notification for the same reference and status arrives, **Then** it is acknowledged successfully and no second set of tickets is issued and no second email is sent.
4. **Given** a notification presenting no bearer token, or one that does not match this project's API key, **When** it arrives, **Then** it is refused, nothing is changed, and the attempt is recorded.
5. **Given** a notification carrying a reference that matches no order, **When** it arrives, **Then** nothing is changed, it is recorded, an operational signal is raised, and it is still acknowledged so the gateway stops retrying it.
6. **Given** any notification the system accepts, **When** it is processed, **Then** the raw payload, the provider, the gateway's transaction identifier, and the gateway's own status value are recorded for audit.
7. **Given** the guest has their payment page open, **When** the order becomes paid, **Then** the page switches to the paid confirmation within seconds with no user action.
8. **Given** a notification the system acts on, **When** it is handled, **Then** the acknowledgement is written within the gateway's 5-second timeout, measured from receipt.
9. **Given** the gateway's first attempt is answered too slowly or with a server fault, **When** it retries the same notification up to three more times, **Then** the order reaches the same final state it would have from a single delivery, and tickets are issued and emailed exactly once.
10. **Given** an order that is already paid, **When** a notification reports the payment was rejected, cancelled, or expired, **Then** the order stays paid, its tickets stay valid, its seats are not returned to the pool, an operational signal is raised at a severity that reaches whoever watches production, and the contradiction is recorded on the order's own record so anyone who looks the order up sees it.
11. **Given** the same already-paid order, **When** a notification simply repeats the completion, **Then** it is recorded and passes quietly, raising no signal and appearing in no queue.
12. **Given** any notification the system answers at all, **When** the answer is written, **Then** it carries a JSON body in the system's standard envelope rather than an empty body — including the authentication refusal and the unreadable-body refusal.
13. **Given** a notification the system takes, **When** it is acknowledged, **Then** the body carries the ordinary success code and no data, identically for one that was acted on and one that was recorded and deliberately not acted on.

### User Story 3 - Unsuccessful and terminal outcomes release the held quota (Priority: P2)

Not every payment succeeds. When the gateway reports that a transaction was rejected, cancelled, or expired, the order must reach a matching terminal state and the seats it was holding must go back on sale. When the gateway reports something the system does not recognise, the order must be left exactly as it is and a human must be told.

**Why this priority**: Getting this wrong quietly destroys inventory — either seats stay locked forever behind dead orders, or they are released while a payment is still live. It is not needed to demonstrate a first successful purchase, so it follows User Stories 1 and 2.

**Independent Test**: For each non-success gateway status, deliver a notification for a pending order and confirm the order reaches the expected state and the ticket type's available quota returns to its pre-order value exactly once.

**Acceptance Scenarios**:

1. **Given** a pending order, **When** a notification reports the payment was rejected or cancelled, **Then** the order is cancelled and its reserved quota is returned to the pool.
2. **Given** a pending order, **When** a notification reports the payment expired, **Then** the order is marked expired and its reserved quota is returned to the pool.
3. **Given** a pending order, **When** a notification reports the payment is still pending, **Then** the order and its quota are left untouched and the guest's page continues to wait.
4. **Given** a pending order, **When** a notification reports an indeterminate outcome, **Then** the order and its quota are left untouched, the notification is recorded, and an operational signal is raised for manual review.
5. **Given** a notification carrying a status value the system does not recognise at all, **When** it arrives, **Then** it is treated the same as an indeterminate outcome — nothing changes, and an operational signal is raised.
6. **Given** an order the gateway itself rejected or cancelled, **When** a notification reports the payment was completed, **Then** the order is not revived, no tickets are issued, the notification is recorded in full, and an operational signal is raised so the money received can be dealt with by a person. (The *expired* case is the opposite and belongs to User Story 6: expiry is this system's own verdict, reached because a notification never came, so a completion reverses it.)
7. **Given** an order whose deadline passes with no notification at all, **When** the expiry sweep runs, **Then** the order is expired and its quota released, exactly as it is today.

### User Story 4 - Gateway connection is configured through the environment (Priority: P2)

An operator points the system at a Manjo gateway environment through deployment configuration, the same way every other external dependency is configured. Configuration that is missing or unusable stops the system at startup with a message naming the problem, rather than passing review and failing on the first guest's checkout.

**Why this priority**: A misconfigured gateway fails every payment, and payment is the only thing this feature exists to do. Catching it at startup rather than on a live guest is the difference between a deploy that fails and an event that does. It follows the payment path itself because a first end-to-end payment can be demonstrated with a single correct configuration.

**Independent Test**: Start the system three times — with the gateway address absent, with it set to something unusable, and with it correct. The first two must refuse to start and say why; the third must open sessions against the configured address.

**Acceptance Scenarios**:

1. **Given** a configured gateway address, **When** a payment session is opened, **Then** the request goes to that address rather than to one fixed at build time.
2. **Given** no gateway address is configured, **When** the system starts, **Then** it refuses to start and names what is missing — there is no default address to fall back to.
3. **Given** a configured address that is not usable, **When** the system starts, **Then** it refuses to start and names the problem.
4. **Given** the configuration is changed and the system restarted, **When** the next payment session is opened, **Then** it goes to the new address.
5. **Given** an operator reads the system's logs, errors, or traces after a failed session, **When** they look for the cause, **Then** they find the address and the failure but no credential value.

### User Story 5 - Guest sees a recognisable, self-explanatory QRIS payment page (Priority: P2)

The guest lands on the payment page and sees the code presented the way QRIS codes are presented everywhere else in Indonesia — inside the standard printed frame carrying the merchant's name and registration number — next to a summary of exactly what they are paying for and a plain step-by-step of how to pay. While the payment is outstanding the primary action is inert and says the system is waiting; the moment the payment confirms, it becomes the action that takes them to their tickets.

**Why this priority**: The code from User Story 1 is only useful if a guest trusts it and knows what to do with it. The standard frame is how a payer verifies they are paying the right merchant before entering a PIN, and the state-driven action is how they learn the payment landed. It depends on User Stories 1 and 2 being in place, so it follows them.

**Independent Test**: Open the payment page for an unpaid order and confirm the framed code, the fee breakdown, the countdown, the payment instructions, and the inert "waiting" action all render from real order data; then confirm the payment and watch the action become the route to the tickets.

**Acceptance Scenarios**:

1. **Given** an unpaid order with an issued code, **When** the payment page loads, **Then** the code is shown inside the standard QRIS frame. *Amended by spec 020: the frame no longer carries the merchant name, registration number or terminal label — it shows the QRIS and GPN marks, the heading and subtitle, the code, the two standard notices and the pay-step icons, per that spec's `contracts/ui.md`.*
2. **Given** the same page, **When** it loads, **Then** it shows the amount due, and an order summary listing the event, venue, dates, each ticket line with its quantity, the subtotal, each applicable fee as its own line, and the total.
3. **Given** the same page, **When** it loads, **Then** a countdown shows the time left to pay alongside a statement that the order is cancelled automatically when it runs out.
4. **Given** a guest unfamiliar with QRIS, **When** they open the payment instructions, **Then** they see an ordered list of steps that names verifying the amount before confirming. *Amended by spec 020: the merchant-name half was removed with the frame text it referred to; the exact amount now carries the whole check.*
5. **Given** an order that is not yet paid, **When** the page is displayed, **Then** the primary action is visibly inert and states that the system is waiting for payment.
6. **Given** the guest's page is open, **When** the payment confirms, **Then** the primary action becomes active and leads the guest to their tickets, with no manual reload.
7. **Given** an order that has expired or been cancelled, **When** the page is displayed, **Then** no scannable code and no countdown are shown, and the guest is told the order can no longer be paid.
8. ~~**Given** the configured merchant identity, **When** it is compared against a code the gateway genuinely issues, **Then** the two agree — checked before go-live and again whenever the merchant account changes.~~ *Retired by spec 020 with FR-021b: nothing is displayed that could disagree with the code.*
9. **Given** the live stream is healthy, **When** the page is open, **Then** it issues no repeating status reads.
10. **Given** the stream is refused, unsupported, or held open by an intermediary that forwards nothing, **When** the payment confirms, **Then** the page still shows it via the fallback, without the guest reloading or acting.
11. **Given** the guest left the page to pay in their banking app and returns, **When** the page reconnects, **Then** it shows the order's current status from the reconnection alone.
12. **Given** the fallback engaged and the stream later recovers, **When** it does, **Then** the repeating reads stop and the guest sees no duplicate, flickering, or contradictory status.

### User Story 6 - A lost notification is recovered by asking the gateway to resend it (Priority: P2)

A guest calls support: they paid, they have the receipt in their banking app, their order expired and they never got their tickets. The resolution is a business process, and most of it happens outside this system — the guest gives ops their proof, ops satisfies itself the payment is real, and ops decides to honour it. What ops then does *inside* this system is narrow: look the order up by its number, top up the ticket quota if the seats have since been sold to someone else, and ask the gateway to resend that transaction's notification. The redelivered notification settles the order through the same path any other confirmed payment takes.

No person ever asserts inside this system that a payment happened. That is the point of the design rather than a limitation of it: the gateway stays the single source of payment truth, so there is exactly one code path that can turn a payment into tickets, and it is the one exercised on every ordinary purchase rather than one that only runs on the worst day of the month.

The system still holds the opposite case — an order the gateway confirmed and has since contradicted. It will not reverse a payment on its own, so those orders wait for a person to choose between refunding and honouring the ticket.

**Why this priority**: The gateway retries a failed callback three times over roughly thirty seconds and then stops. Any deploy, restart, or brief database outage inside that window strands a paying customer. Without a recovery route the only remedy is a refund, and by then the seats have been resold.

**Independent Test**: Take an order, suppress its notification entirely, let it expire and its seats return to the pool. Then top the quota back up and replay the notification. Confirm the order moves to paid, the tickets are issued once, the email is sent once, and the seats are deducted again so the count stays truthful.

**Acceptance Scenarios**:

1. **Given** an order a guest claims to have paid, **When** ops looks it up by its order number, **Then** they see its status and every notification recorded against it — the gateway's transaction identifier, the raw status, and the arrival time — including notifications that were refused.
2. **Given** an expired order whose quota covers its full hold, **When** the gateway redelivers the completed-payment notification, **Then** the order becomes paid, its seats are deducted again, and the tickets are issued and emailed through the same path a first-time notification would use.
3. **Given** an expired order whose ticket type no longer has enough quota for the whole order, **When** the notification is redelivered, **Then** the order's status is unchanged, no tickets are issued, no quota moves, and the response reports that the tickets are unavailable — carrying an envelope code that separates it from an ordinary acknowledgement despite an identical status line, and naming each ticket type short of covering the order and by how much, so the top-up can be sized from the response alone — while still being acknowledged so the gateway does not retry an attempt that would fail identically.
4. **Given** that same order, **When** ops adds the missing quota and asks for the notification to be resent again, **Then** it settles normally.
5. **Given** an order already settled this way, **When** the notification is delivered again, **Then** no second set of tickets is issued, no second email is sent, and the seats are not deducted twice.
6. **Given** a paid order the gateway has since contradicted, **When** ops looks that order up by its number, **Then** the contradicting notification is shown alongside the one that confirmed the payment, in the order they arrived — and the operational signal the contradiction raised is what brought ops to look.
7. **Given** such an order, **When** ops reviews it, **Then** they can see enough to choose between refunding and honouring the ticket, and the system has taken neither action on its own.

---

### Edge Cases

- A contradiction and a routine retry look identical on the wire — both are simply another notification for a paid order. Only the reported status separates them, so discriminating wrongly either buries the contradiction or floods the alert with the retries FR-012c guarantees.
- A contradiction arrives for an order whose tickets have already been scanned at the door.
- The gateway contradicts a payment, staff decide to honour the ticket, and a further notification then contradicts it again.
- Two notifications for the same reference arrive at the same moment. Only one may issue tickets.
- A guest loses or cannot scan their only code — their app rejects it, they close the page, or the image fails to render. With no way to obtain a replacement, the sole recourse is to let the order expire and book again.
- A notification reports a withdrawal rather than a deposit on an endpoint that only ever expects deposits.
- The notification carries no amount, so a payment for the wrong amount cannot be detected from the notification alone. The code itself encodes the amount, which is what makes this tolerable — but it also means an amount discrepancy could only ever originate on our side.
- A percentage fee against an odd subtotal yields fractional rupiah — 11% of 105,001 is 11,550.11 — so the total payable carries centavos that Indonesian payment practice does not use. The gateway preserves such an amount verbatim rather than rejecting, truncating, or rounding it: a session opened for 11,550.11 returns a code carrying exactly that figure, so the guest is charged what they were shown.
- The notification's transaction date is unparseable, in an unexpected format, or far in the past or future.
- The gateway answers a session request with a success flag but a malformed or unexpected method payload.
- The gateway answers slowly enough that the guest's checkout request times out, while the session is in fact opened on the gateway's side. A retry then reaches a gateway that already holds a session under that reference.
- A retry after a timeout is answered with a duplicate-reference error: the gateway holds a code this system never received and has no way to fetch. The order is unpayable from the moment it is created, and nothing about it looks broken until someone asks why it expired.
- The retry budget is exhausted while the guest waits, so checkout fails on an order whose session may or may not exist at the gateway — the two cases are indistinguishable until a retry draws the duplicate-reference error.
- A code exists at the gateway for an order this system has already released. It expires unpaid, but until it does, the two systems disagree about what is outstanding.
- The gateway environment is changed while unpaid orders issued against the previous one are still live. Their codes were issued elsewhere, and no callback for them will authenticate against the new environment's key.
- A deployment carries a stale gateway address — a sandbox or development endpoint reaching production. Nothing in the configuration declares which environment was intended, so the system starts cleanly and takes real orders against the wrong gateway.
- The gateway sends a notification while the system is restarting or the database is briefly unavailable. Its retry budget is finite — 3 retries, 10 seconds apart — so an outage longer than roughly 30 seconds exhausts it and the notification is lost for good.
- Post-payment work (ticket issuance, email) is still running when the acknowledgement is written, and the process is stopped before it finishes. The gateway has already been told 200, so it will never retry.
- A notification is answered slowly enough that the gateway times out at 5 seconds and retries, while the first attempt is still mid-flight — two deliveries of the same notification processing concurrently.
- The settle refusal and an ordinary acknowledgement leave on an identical 200 status line, so anything branching on the status alone — a test, an intermediary, a log that records only the code — reads a refusal as a success. Only the envelope code separates them, which is what makes it the thing that has to be asserted on rather than the status.
- The API key is rotated while the gateway still holds the previous one, so genuine callbacks fail authentication until both sides agree again.
- A future change to the order-number format pushes the reference past the gateway's 25-character limit — silently, unless the limit is enforced on our side. The current format leaves 6 characters of headroom.
- A guest paid, the notification was lost, the order expired, and the seats were resold before anyone noticed. A redelivered notification cannot settle it without overselling, so it is refused until someone adds quota — and if the event is sold out and no more seats can be added, a refund is the only outcome left.
- Ops adds quota and requests a resend, and the added seats are bought by someone else before the redelivered notification arrives. The settle is refused a second time on the same shortfall.
- Ops requests a resend twice in quick succession, so two redelivered notifications for the same transaction arrive together. Only one may settle the order and take its seats.
- The redelivered notification arrives while the order is being looked at, or while a second operator is topping up the same ticket type. The quota check and the settle must agree with each other, not with what either party saw a moment earlier.
- The live stream is refused because several guests share one public address — a venue's network, an office, a mobile carrier's shared address — and the concurrent-stream limit is reached. A refusal is an answer, not a dropped connection, so the browser does not retry it on its own.
- An intermediary holds the stream open and forwards nothing. The connection reports itself healthy, no error is raised, and without a liveness check nothing on the page ever notices.
- The guest's browser suspends or discards the page while they pay in their banking app, and the stream is gone when they return.
- The stream recovers while a fallback read is already in flight, so the same status arrives twice by two routes.
- The merchant account behind the gateway changes, so the code now encodes a different merchant than the frame's fixed labels claim — and the payment instructions go on telling guests to verify a name the code no longer carries. Nothing detects this automatically while the labels are fixed.
- The gateway returns an expiry the system's contract definition does not know about, so it is dropped during decoding and the system silently falls back to its own deadline — the two sides then enforce different ones with nothing reporting the divergence.
- The returned expiry is already in the past when it arrives, is unparseable, or carries an unexpected offset.
- The expiry field is absent entirely. Depending on how it is represented, an absent timestamp may arrive as a valid-looking value far in the past rather than as nothing at all — indistinguishable from a genuinely expired code unless treated as the missing case.
- The expiry is malformed in a way that fails the decode of the whole response, taking the still-perfectly-good payload down with it and denying the guest a code over a field that only affects the countdown.
- The gateway's default window is much longer than expected, so orders hold their seats out of sale far longer than intended — invisible unless the difference is reported, since nothing is requested to compare against.
- The gateway's default window changes on their side with no notice to us; the first symptom is inventory behaving differently.
- A caller sends a resend body the endpoint cannot read an order number from — the observed case was a payload encoded twice, so the field the endpoint keys on was not there to find. The press was answered as accepted, sent nothing, and left no trace; the next press was refused, because the unreadable one had been counted against an allowance every other order shares.
- The resend cooldown expires on the server while the page is still counting down, or the reverse, because the two clocks disagree. The page's countdown is a display of a number the server gave it, not an authority — the next press is what settles it either way.
- The server restarts while a guest is mid-countdown, so the cooldown it was counting no longer exists anywhere.
- Two tabs are open on the same confirmation screen. Each counts independently, so one can show an armed button while the other counts down, and a press from either is subject to the same single server-side window.
- A guest presses resend for an order whose email is genuinely undeliverable — a mail outage, or an address that bounces. Every press spends the window, and every press is answered identically, so nothing on the screen ever says the mail is not arriving.

## Requirements *(mandatory)*

### Functional Requirements

#### Opening a payment session

- **FR-001**: System MUST open payment sessions by sending a JSON request to the gateway's transaction path (`/v1/manjo/transaction/incoming`) beneath the stored base address, and MUST NOT make any outbound call to the previous payment provider for any new order.
- **FR-002**: Each session request MUST carry the six fields the gateway requires: the order's reference identifier, the amount due as an absolute numeric value, the currency, the payment method, the merchant network account with its credential, and a human-readable remark identifying the purchase. The method-specific payload is omitted for QRIS.
- **FR-002a**: The gateway credential is carried inside the request body rather than in an authorization header. It grants no privilege (FR-028a), so the body is not secret — but System MUST still keep the pair out of guest-facing responses, and MUST be able to change it without a data migration should the gateway ever begin enforcing it as a real credential.
- **FR-002b**: The amount sent MUST be the order's total payable — the ticket subtotal, plus each percentage fee computed against that subtotal, plus each flat fee — and MUST be byte-for-byte the figure the guest is shown as the total. Rounding MUST happen once, when the fee lines are frozen onto the order, never again when the request is built.
- **FR-002c**: System MUST NOT send a requested expiry. The gateway applies its own window and reports it back (FR-009), so sending one would create a second opinion about a deadline the system does not own.
- **FR-003**: System MUST treat only an explicitly successful gateway response as a valid session; any response carrying a failure indication or a gateway error MUST be treated as a failed session.
- **FR-004**: System MUST record the gateway's external reference for the transaction against the order so a payment can be traced end to end by support.
- **FR-005**: System MUST store the raw QRIS payload returned by the gateway and render the scannable image from it on demand; no image file is stored.
- **FR-006**: System MUST treat a successful response with an empty or unusable QRIS payload as a failed session rather than presenting an unscannable code to the guest.
- **FR-007**: When a session cannot be opened for any reason, the guest MUST see an actionable message, the order MUST remain unpaid, and its reserved quota MUST remain held so the guest can retry.
- **FR-007a**: When opening a session fails on a timeout or a network error, System MUST retry a small bounded number of times before reporting failure to the guest. A transient blip must not end a checkout the guest did nothing wrong in.
- **FR-007b**: Every retry MUST reuse the order's reference unchanged. The gateway rejects a reference it has already issued a code for, so reuse is what guarantees a retry can never produce a second live code for one order — FR-010 holds by the gateway's own enforcement, not by our care alone.
- **FR-007c**: Retries MUST be bounded in total elapsed time, because a guest is waiting on the response. Checkout MUST fail visibly rather than hang; the gateway's own callback client waits far longer between attempts than a person will, and that pacing MUST NOT be copied here.
- **FR-007d**: A duplicate-reference error MUST be recognised as its own outcome, not folded into generic failure. It means the gateway holds a code for this order that this system never received and cannot obtain — there is no call that returns an existing code (FR-022). Retrying further cannot help, and the order can never be paid, because the guest is never shown a code.
- **FR-007e**: On a duplicate-reference error, System MUST NOT leave the order holding its seats until the deadline. The seats MUST be returned to the pool promptly and the guest MUST be told plainly that the attempt failed and to start again, rather than being shown a payment page with no code or a countdown that cannot end in a payment.
- **FR-007f**: Should a payment nonetheless arrive for such an order, it MUST be recorded and MUST raise an operational signal distinguishable from routine traffic, rather than being silently accepted or silently dropped. It MUST NOT settle the order under FR-019: that order was released because no code ever reached the guest, so a payment against it did not come from this booking, and the guest was told to start again and may hold a second order. This is a case for a person, reached through the operational signal and the per-order lookup (FR-022c).
- **FR-008**: System MUST NOT open a payment session from inside a database transaction; the order and its quota hold are committed first, and the session is opened after.
- **FR-008a**: The full purchase flow MUST be exercisable end to end against a substitute endpoint speaking the same contract, with no reachable gateway and no vendor library standing between the system and the wire. This capability exists today and MUST survive the migration: it is what allows the request shape, the response parsing, the expiry handling, and the callback authentication to be verified without a network.
- **FR-009**: The payment deadline MUST be taken from the expiry the gateway returns with the session, so the deadline the guest counts down to, the deadline the expiry sweep enforces, and the deadline the payment network enforces are the same instant.
- **FR-009a**: The returned expiry carries a UTC offset. System MUST preserve the instant it denotes rather than its local wall-clock reading — through parsing, storage, and every surface that serves it — so a guest in any timezone sees the same remaining time.
- **FR-009b**: When the gateway returns no expiry, or one that cannot be read, or one already in the past, System MUST fall back to a deadline computed from its own configured payment window and MUST raise an operational signal — the two sides would otherwise enforce different deadlines with no way to notice.
- **FR-009c**: Any usable expiry the gateway returns MUST be adopted as the deadline, whatever its length. System MUST NOT cap it, shorten it, or substitute its own — the code's lifetime and the order's deadline are the same instant, and that is what makes a single non-refreshable code (FR-010) safe.
- **FR-009d**: The configured payment window remains as an expectation, not a request: System MUST raise an operational signal when an adopted expiry differs materially from it. A window far longer than expected holds seats out of sale for as long as it lasts, and nothing else would reveal that the gateway's default had changed.
- **FR-009e**: A malformed expiry MUST NOT cost the guest a usable code. When the expiry cannot be read but the payload can, System MUST take the FR-009b fallback and show the code rather than discard an otherwise-valid session. An unreadable timestamp is a deadline problem, not a reason the guest cannot pay.
- **FR-010**: An order MUST have exactly one payment session for its lifetime. The mid-window code refresh is withdrawn: there is no second session, no per-attempt reference suffix, and no path that opens a new session for an order that already has one.
- **FR-010a**: The reference sent to the gateway is the order number itself, unmodified. It occupies 19 of the 25 permitted characters (`ORD-` + an 8-digit date + `-` + a 6-character code). System MUST guarantee the limit by construction rather than by truncation, and MUST refuse to open a session with an over-length reference rather than send one the gateway will reject.
- **FR-010b**: Because a notification's reference is now exactly an order number, matching a notification to its order MUST be a direct lookup. No suffix stripping, pattern matching, or normalisation may sit between the two.
- **FR-010c**: The code stays valid for the whole payment window because the window *is* the code's own lifetime (FR-009). Nothing may extend an order's deadline, issue a replacement code, or present the guest with an action that appears to do either.

#### Receiving gateway notifications

- **FR-011**: System MUST expose a dedicated endpoint at `/v1.0/callback/exec` that accepts payment notifications from the Manjo gateway. The path is fixed by the gateway's dispatch code and is not ours to choose.
- **FR-012**: System MUST authenticate every notification by comparing the bearer token the gateway presents against an API key this project owns. A notification presenting no token, or a token that does not match, MUST be refused, MUST change nothing, and MUST be recorded as a refused attempt.
- **FR-012a**: The comparison MUST NOT leak whether a presented token is partially correct, and the API key MUST be rotatable without a code change.
- **FR-012b**: System MUST answer every callback within the gateway's 5-second timeout. Work that cannot be guaranteed to finish inside that budget MUST happen after the response, not before it.
- **FR-012c**: The gateway retries any non-200 answer up to 3 times, 10 seconds apart. System MUST therefore answer 200 for every notification it has authenticated and durably recorded — including ones it deliberately does not act on (unrecognised reference, unexpected transaction type, unrecognised status, already-final order). A non-200 MUST be reserved for a failed authentication and for transient internal faults where a retry is genuinely the right outcome.
- **FR-012d**: Because retries are certain rather than hypothetical, the outcome of a notification MUST survive being delivered up to 4 times in total without duplicating any effect.
- **FR-012e**: Every answer the callback endpoint gives MUST carry a JSON body in the same `{code, message, data}` envelope every other endpoint in this system uses. An acknowledgement MUST NOT be an empty body, and the FR-019c refusal MUST NOT be a bare object sitting outside the envelope — one shape per path is a shape that has to be learned per path. The gateway does not read the body at all, so this body is not for the caller: it is what the substitute gateway of FR-008a asserts against and what an operator reads from a captured response.
- **FR-012f**: An acknowledgement MUST carry no data, and every *uneventful* outcome MUST answer identically — the payment applied, a pending notification, and a repeat that restates an outcome already recorded all return the same envelope, the ordinary success code, and a null `data`. What such a notification did MUST NOT be reported in the response: it is recorded under FR-018 and read under FR-022c, and a second account of it in a transient body could disagree with the durable one. At-least-once delivery makes the repeat the *normal* case rather than an anomaly, which is why it belongs here and not under FR-012g.
- **FR-012g**: Every outcome that raises an operational signal MUST name itself in the envelope's code, so the caller learns what the operator learns. These are the notifications the system records but deliberately does not act on: an unrecognised reference (FR-013), a transaction that is not a deposit (FR-020), an indeterminate or unrecognised status (FR-014), a contradiction of an order already paid (FR-016b), and a completion for an order the gateway itself cancelled (FR-019d). Each MUST keep its 200 status per FR-012c, so the status line cannot distinguish them and the code is what must — the same device FR-019e uses for the settle refusal, applied to the whole set rather than to one member of it.

  The rule is the operational signal, not whether the order moved. An outcome worth telling a human about is worth telling the caller about; one that is merely uneventful is not, and flagging it would bury these five in exactly the retry noise FR-012c guarantees. This supersedes the earlier decision that every 200 answered identically: uniformity across *anomalies* made a notification that changed nothing look the same as one that worked, so the only way to find out that a reference matched no order was to go reading logs.

  The message MUST name the kind of problem without restating order-specific detail. The endpoint is authenticated, so this is not the enumeration concern that governs the resend endpoint (FR-021l) — it is that the durable record is the account of what happened, and a response that duplicated it could drift from it.
- **FR-013**: System MUST match an authenticated notification to an order by the reference identifier the system itself supplied when opening the session. A notification whose reference matches no order MUST change nothing, MUST be recorded, MUST raise an operational signal, and MUST still be acknowledged per FR-012c — retrying it three more times would not make the order exist.
- **FR-014**: System MUST map the gateway's reported status onto an order outcome according to this table, which is total — every possible value has a defined result:

  | Gateway status | Order outcome | Reserved quota | Operational signal |
  | --- | --- | --- | --- |
  | Pending | unchanged | stays held | no |
  | Completed | paid | consumed | no |
  | Reject | cancelled | released | no |
  | Cancel | cancelled | released | no |
  | Expired | expired | released | no |
  | Obscure (indeterminate) | unchanged | stays held | yes |
  | any unrecognised value | unchanged | stays held | yes |

- **FR-015**: System MUST acknowledge every authenticated notification immediately, before ticket issuance, email dispatch, or any other post-payment work begins.
- **FR-016**: Notification handling MUST be idempotent: repeated notifications for the same order and outcome MUST be acknowledged without re-applying the outcome, and tickets MUST be issued at most once per order.
- **FR-016a**: A paid order MUST NOT be moved by any later notification, whatever it reports. Payment is final in this system's record. Note the asymmetry this creates with FR-019, and that it is deliberate: a completion may revive an expired order, but nothing revokes a completion. The gateway may tell us about a payment we missed; it does not get to take one back once tickets are in a buyer's hands.
- **FR-016b**: System MUST tell a benign repeat apart from a contradiction, because both arrive as "another notification for a paid order" and only the reported status separates them. A notification repeating the outcome already recorded MUST pass quietly — retries are routine and guaranteed by FR-012c. A notification reporting rejection, cancellation, or expiry against an order already paid MUST raise an operational signal distinguishable from that routine traffic, not one buried at the same level.
- **FR-016c**: A contradiction MUST raise an operational signal at a severity that reaches whoever watches production, and the contradicting notification MUST be visible on the order's own record (FR-022c) so that anyone who looks the order up sees it without being told to look. This is deliberately a *reactive* route rather than a queue somebody is expected to patrol — see FR-022h.
- **FR-016d**: Surfacing a contradiction MUST NOT revoke issued tickets, recall delivered emails, or return seats to the pool. By the time one arrives the tickets exist and the seats may have been resold, so the choice between refunding and honouring the ticket belongs to a person.
- **FR-017**: Concurrent notifications for the same order MUST result in the outcome being applied exactly once.
- **FR-018**: System MUST record every notification it accepts or refuses, retaining the raw payload, the provider, the gateway's transaction identifier, and the gateway's own status value in its original form so distinct failure reasons remain distinguishable after mapping.
- **FR-019**: A notification reporting a completed payment for an order that is already cancelled or expired MUST settle that order, issuing and delivering tickets through the same path any other confirmed payment takes. It is matched to its order by the reference the notification carries, so it settles only the order the gateway names — never a class of orders sharing a status. It MUST be recorded in full and MUST raise an operational signal, because settling an order the deadline had already released is not routine traffic and someone should be able to see that it happened.
- **FR-019a**: This is the recovery path for a lost notification (FR-022b), and it is deliberately the *only* one. An operator asks the gateway to redeliver the notification for that transaction; the redelivered notification settles the order exactly as the original would have. No person ever asserts inside this system that a payment happened — the gateway remains the single source of payment truth, and there is exactly one code path that can turn a payment into tickets.
- **FR-019b**: Settling a released order MUST take its seats back, in the same transaction as the status change, so the remaining-quota count stays truthful. The order's hold is restored in full or not at all.
- **FR-019c**: When the quota does not cover the order's full hold, the system MUST NOT settle: the status is unchanged, no tickets are issued, and no quota moves. It MUST answer the notification with a success status carrying an error describing the unavailability, so the gateway does not spend its retry budget on an attempt that would fail identically. Recovery is for the operator to add quota and request another resend — a partial settle is never an outcome, because half an order is not a thing this system can issue tickets for.
- **FR-019d**: Only an order that expired against its deadline is eligible. An order the gateway itself rejected or cancelled MUST NOT be settled by a later completion — that is the contradiction case (FR-016b), not the lost-notification case, and the two must not be conflated.
- **FR-019e**: The refusal MUST be tellable from an ordinary acknowledgement by the envelope's code alone, because both leave on a 200 status line and FR-012f empties the body of everything else. It MUST carry a registered sub-code in the 200 band — `200001`, paired with the `TICKETS_UNAVAILABLE` machine-readable code — rather than the ordinary success code, so the numeric scheme's `status × 1000 + sub-code` shape holds and no envelope code contradicts the status it sits behind. It MUST carry in `data` each ticket type short of covering the order's hold and by how much: this is the one exception to FR-012f, and it exists because the operator who will request the next resend has to size the top-up, and the figure is not derivable from the sold count shown elsewhere in the admin surface (FR-022e).
- **FR-020**: A notification reporting a transaction type other than a deposit MUST change no order, MUST be recorded, MUST raise an operational signal, and MUST be acknowledged per FR-012c.
- **FR-021**: The order lifecycle, ticket issuance, and ticket delivery MUST be unchanged by this migration apart from which provider issues and confirms the payment, **and one deliberate exception**: FR-019 adds a transition out of the expired state, which previously had none. Every other state and transition is untouched, and the exception is stated here rather than left to be discovered because it is the first thing in this feature that genuinely alters the lifecycle. The guest-facing payment page changes as User Story 5 describes and by the withdrawal of two capabilities: the status-check action (FR-022a) and the mid-window code refresh (FR-010). Ticket delivery is unchanged in what it sends and when: FR-021j–q govern only how the confirmation screen's resend control reports its cooldown, not what an email contains or which event causes one.

  **Superseded by [spec 020](../020-qris-frame-simplify/spec.md) FR-001 to FR-006.** The
  frame remains; the three identity fields do not. What it may show is enumerated in
  [spec 020 `contracts/ui.md`](../020-qris-frame-simplify/contracts/ui.md).
- **FR-021b**: ~~Because those values are fixed rather than derived, they MUST be verified against a code the gateway genuinely issues before go-live, and re-verified whenever the merchant account changes.~~
  **Retired by spec 020.** The requirement existed because a fixed label could disagree
  with the code it sat beside. With nothing displayed there is no label to disagree, so
  the release-time verification step and the mismatch edge case go with it. This is the
  one clear gain of the change and worth recording as such.
- **FR-021c**: The payment instructions MUST tell the guest to verify ~~both the merchant name and~~ the amount before confirming.
  **Narrowed by spec 020 FR-010/FR-011.** The merchant-name comparison was removed by
  explicit decision, which leaves the amount carrying the whole of the guest's in-page
  defence against a swapped code — hence spec 020's requirement that the exact figure be
  stated rather than a generic "check the amount".
- **FR-021d**: The payment page MUST learn of status changes from a live server-pushed stream, and MUST NOT read the order on a fixed interval while that stream is healthy.
- **FR-021e**: The page MUST judge the stream healthy only while it is both connected *and* delivering. If no frame and no keep-alive arrives within twice the server's keep-alive interval, the page MUST treat the stream as failed regardless of what the connection itself reports — a stream held open by an intermediary that never forwards anything looks identical to a working one, and is otherwise undetectable.
- **FR-021f**: While the stream is failed — refused, unsupported, errored, or silent under FR-021e — the page MUST fall back to reading the order periodically, and MUST stop as soon as the stream is healthy again.
- **FR-021g**: Recovery MUST be automatic. It MUST NOT require the guest to reload, retry, or notice which channel is in use: the same confirmation appears in the same place, whichever delivered it.
- **FR-021h**: A newly opened stream MUST deliver the order's current status before any subsequent change, so a guest returning from their banking app is brought up to date by reconnection alone.
- **FR-021i**: The per-address limit on concurrent streams MUST accommodate several guests sharing one public address — a venue's network or a mobile carrier's shared address is the normal case for this audience, not an edge one — and being refused MUST engage the FR-021f fallback rather than leaving the page with no channel at all.

#### Resending the ticket email from the confirmation screen

The endpoint is spec 008's FR-022; what follows governs the cooldown it enforces and the confirmation screen built in this feature that presents it.

- **FR-021j**: Every answer the resend endpoint gives — accepted or refused as rate-limited — MUST carry the number of whole seconds remaining before another resend for that order will be accepted. An acceptance carries the full cooldown it has just started; a refusal carries what is left of the one already running. The screen MUST take the wait from that number and MUST NOT derive it from its own clock, from the time of its own last press, or from a window compiled into the page — a locally-guessed countdown re-enables the button whenever the two disagree, which produces a second refusal in place of a send.
- **FR-021j-i**: When an answer carries no such number — an older deployment, an intermediary, an error path that lost the detail — the screen MUST still hold the button for a brief fixed floor rather than leaving it live. A missing number is not permission to press again immediately: with no hold at all, a held key becomes a burst of refusals, which is the loop FR-021j exists to break. The floor MUST be markedly shorter than any real window, so it reads as "ask the server again shortly" rather than as an invented deadline a guest could be stranded behind. This does not weaken FR-021j: the floor applies only where the server said nothing, and the next press takes whatever the server does say.
- **FR-021k**: A resend request whose body yields no order number — malformed, wrongly encoded, or missing the field — MUST be refused with a validation error before the cooldown is consulted, and MUST consume no allowance of any kind. The endpoint MUST NOT hold a bucket shared between requests it could not key: one such bucket makes any single malformed request, from any caller, a refusal for every other guest for the length of the window.
- **FR-021l**: The identical-answer rule that hides whether an order exists MUST apply only to an order number that is well-formed but not found. A body the endpoint cannot read carries no claim about any order, so refusing it discloses nothing and MUST NOT be disguised as acceptance — a caller told "sent" when nothing was sent is a defect the guest is left to discover from an inbox that never fills.
- **FR-021m**: Every attempt that gets past the body check MUST spend the order's cooldown, whatever its outcome — a delivered email, an order number that is not found, an order that is not payable, and a send that failed all count the same. The endpoint is unauthenticated, so the limit MUST cap the work an attempt causes rather than only the mail it produces; counting deliveries alone would leave order-number probing unrestricted. The cost is that a send failing on our side holds the guest back for a window, which is accepted because it keeps the seconds returned under FR-021j meaning one thing.
- **FR-021n**: Every resend attempt MUST be recorded server-side with the outcome it actually had — delivered, order unknown, order not payable, refused for cooldown, or body unreadable — naming the order number it was made against. The record is for the operator, not the caller: the answer on the wire stays identical across every outcome the identical-answer rule covers. An outcome that leaves no trace is indistinguishable from a press that never happened, which is precisely how a silently swallowed resend escaped notice.
- **FR-021o**: The screen MUST re-arm the resend button by itself when the countdown reaches zero, without a reload and without any further press. A refusal that disables the control permanently is the defect this requirement exists to prevent: the guest whose email genuinely did not arrive is then left with no way to ask for it again.
- **FR-021p**: The screen MUST NOT persist the cooldown across page loads or share it between tabs. A freshly loaded confirmation screen arms the button, and the first press resolves the true state — a send, or a refusal carrying the seconds still to wait. The cooldown is held in the server's memory and does not outlive a restart, so a deadline remembered by the browser could outlast the limit it describes and hold a guest back from a resend the server would have accepted.
- **FR-021q**: A refusal for cooldown MUST read to the guest as a wait, not as a failure: it MUST say when the resend can be asked for again and MUST NOT be presented in the same terms as a send that genuinely could not be delivered. The two have opposite remedies — one resolves by waiting, the other by trying something else.

#### Reconciling a payment whose notification never arrived

- **FR-022**: The gateway cannot be asked for a transaction's current status, so notifications are the only source of payment truth. System MUST NOT depend on an outbound status query for any correctness guarantee.
- **FR-022a**: The guest-facing "check payment status" action is withdrawn, consistent with the payment page design. The guest's page MUST learn of a confirmed payment from the live update alone, and MUST NOT offer a control whose only honest answer is what the page already shows.
- **FR-022b**: Because the expiry sweep decides on the deadline alone and never consults the gateway, an order whose notification was lost WILL be expired and its quota released. Recovery is by redelivery (FR-019a), not by a staff assertion: the gateway can resend a notification per transaction, so the correct answer to a lost one is to ask for it again rather than to let a person stand in for it.
- **FR-022c**: Staff MUST be able to look an order up by its number and see its current status plus every notification recorded against it — the gateway's transaction identifier, its raw status, and the time it arrived — so the order can be matched against the gateway's own dashboard before a resend is requested. This lookup is the whole of this system's part in the rescue.
- **FR-022d**: The system MUST NOT offer any way for a person to record that a payment happened. Ticket issuance MUST have exactly one trigger: a notification from the gateway. A second trigger would be a second source of payment truth, and it would be the path least exercised and most trusted at the moment it matters.
- **FR-022e**: Before requesting a resend, staff MUST be able to see what the order actually holds — how many seats of which ticket type — and how many of each remain. Without that figure an operator cannot size the quota top-up FR-019c's failure branch depends on, and the number available elsewhere in the admin surface counts released orders and so overstates what has been sold.
- **FR-022h**: There MUST NOT be a standing worklist of orders awaiting attention. Every order is reached by its number (FR-022c); anomalies reach a person through operational signals (FR-016c, FR-007f, FR-019).

  This reverses an earlier decision, and the reasoning is worth keeping. The worklist was justified by "an order nobody knows to search for is not findable" — but the case it was built for, a notification that never arrived, writes no row at all and so never appeared on it. It listed only the two anomalies the system can already detect and shout about, and once manual confirmation is withdrawn nothing removes an entry from it, so it would grow without bound and stop being read. A queue nobody trusts is worse than no queue, because it looks like coverage. Orders needing rescue arrive at ops through the customer, with the order number in hand, which is the route that actually works.

#### Gateway connection configuration

- **FR-023**: The address the system calls, the credential it presents, and the key it authenticates callbacks against MUST all come from deployment configuration rather than being fixed at build time.
- **FR-023a**: No gateway configuration and no gateway credential may be stored in the database. The database holds no part of how this system reaches the gateway.
- **FR-024**: Configuration MUST be read once at startup. A change takes effect on restart; there is no live reload and nothing may imply otherwise.
- **FR-025**: Exactly one gateway environment MUST be active for the whole system at a time. There is no per-request, per-event, or per-order selection.
- **FR-026**: System MUST refuse to start when required gateway configuration is absent, naming what is missing, rather than starting and failing on the first guest's checkout. The base address is required — there is no default, and no gateway hostname may be compiled into the build.
- **FR-026a**: No configuration value may declare which gateway environment is intended. The address is the only statement of where the system points, so nothing can silently disagree with it. The cost is recorded under Assumptions: a stale address cannot be detected as stale.
- **FR-027**: System MUST refuse to start when configured values are present but unusable — an address that is not a valid endpoint, or a timing value outside its permitted range — naming the problem. Because configuration is read only at startup (FR-024), there is no last-known-good state to fall back to and starting anyway would guarantee a failure later.
- **FR-028**: The configuration variables for this gateway MUST be named for the payment gateway generally rather than for the previous provider, so no name outlives the integration it was named after. The mapping is recorded in Clarifications.
- **FR-028a**: The gateway requires the credential pair to be present but attaches no privilege to it. System MUST send it on every session request; it is configured rather than hardcoded so it can be changed without a rebuild.
- **FR-028b**: Moving between gateway environments requires a configuration change and a restart. This is accepted deliberately in exchange for holding no gateway configuration in the database.
- **FR-029**: The callback API key MUST NOT appear in application logs, error messages, traces, or any response. It is the only real secret this integration holds.
- **FR-030**: The timing configuration MUST collapse to a single payment-window value. Three interdependent values exist today — one sent to the provider as the requested validity, one used as the server-owned deadline, and one driving the client's code refresh. The first is no longer sent (FR-002c), the second is no longer ours to decide (FR-009), and the third has nothing left to drive (FR-010). The single survivor serves only as the FR-009b fallback and the FR-009d expectation, and the startup checks that related the three to each other MUST be removed rather than left comparing values that no longer mean what they did.

### Key Entities *(include if data involved)*

- **Payment Session Request**: What the system asks the gateway to open. Carries six required fields — the order reference, absolute amount, currency, payment method, merchant network account with credential, and remark — plus an optional payer name. It carries no requested expiry and no method payload for QRIS.
- **Payment Session Response**: What the gateway answers. Carries a success indicator, an error slot, the payment method it acted on, the gateway's own external reference for the transaction, and a method-specific response — for QRIS, the raw scannable payload, an optional hosted image address, and the expiry the gateway will enforce.
- **Payment Notification**: What the gateway sends to the callback endpoint. Carries the reference the system originally supplied, the gateway's network transaction identifier, the transaction status, the transaction date, a counterparty identifier, a transaction type (deposit or withdrawal), and optional additional information including a retrieval reference number. Authenticated by a bearer token carried on the request, not by anything inside the body.
- **Callback Acknowledgement**: What the callback endpoint answers, in the system-wide `{code, message, data}` envelope. For every notification it takes — applied or deliberately not acted on — the ordinary success code and a null `data`. For the FR-019c settle refusal, the registered 200-band sub-code and the per-ticket-type shortfall in `data`. Never read by the gateway, which acts on the status line alone.
- **Callback API Key**: New secret this project owns and the gateway is configured with. Its only job is to authenticate inbound callbacks. Rotatable, never logged, and distinct from the outbound `client_id`/`client_secret` credential.
- **Gateway Connection Configuration**: Deployment configuration, not stored data — a required base address, the credential pair, the callback key, and the payment window. No environment selector and no built-in hostnames. Read once at startup, one set active system-wide, with no database representation, schema change, or migration.
- **Payment Log Entry**: Existing per-notification audit record — the order it belongs to, the provider, the gateway transaction identifier, the payment type, the gateway's raw status string, and the full raw payload.
- **Order**: Existing. Gains no new lifecycle states; continues to carry the raw QRIS payload, the server-owned payment deadline, and its status.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of new checkouts obtain their payment code from the Manjo gateway, and zero outbound requests reach the previous provider.
- **SC-002**: A guest sees a scannable payment code within 5 seconds of completing checkout in at least 95% of attempts.
- **SC-003**: A guest with the payment page open sees it switch to the paid confirmation within 5 seconds of the gateway reporting a completed payment, without any user action.
- **SC-004**: Replaying the same completed-payment notification 10 times for one order produces exactly one set of issued tickets and exactly one confirmation email.
- **SC-005**: 100% of notifications received — accepted or refused — are retrievable afterwards with their original payload and the gateway's original status value.
- **SC-006**: For every non-success outcome, the reserved quota returns to the pool exactly once, verified by the ticket type's available count matching its pre-order value.
- **SC-007**: An operator can switch the system to a different gateway environment by changing configuration and restarting — no code change and no rebuild. A misconfiguration is caught at startup rather than by a guest.
- **SC-008**: Zero orders end in a state where a payment was confirmed but no tickets were issued and no operational signal was raised.
- **SC-009**: Unpaid orders release their reserved quota within one minute of their payment deadline, unchanged from the current behaviour.
- **SC-010**: A support request naming an order can be traced to the gateway's own transaction reference, and vice versa, in under one minute.
- **SC-011**: 100% of callbacks are acknowledged within 5 seconds of arriving — the gateway's timeout, past which a duplicate delivery is guaranteed rather than merely possible.
- **SC-012**: Zero forged callbacks — requests presenting no token or a wrong one — result in any change to any order.
- **SC-013**: An operator can take a guest's payment receipt and get the stranded order settled end to end — quota topped up if needed, notification resent, tickets issued and emailed — in under 5 minutes, without a developer, a database query, or a deploy.
- **SC-014**: Recovery never oversells: across any number of redelivered notifications, no ticket type's issued count exceeds its quota, and no order is ever settled with only part of its seats.
- **SC-015**: While the live stream is healthy, an open payment page issues no repeating status reads — verifiable as zero periodic requests over a five-minute observation.
- **SC-016**: A confirmed payment reaches the guest's open page within 5 seconds on a healthy stream, and within one fallback interval when the stream has failed — with no guest action in either case.
- **SC-017**: Zero guests remain on "waiting for payment" after a confirmed payment because the live channel failed without being noticed.
- **SC-018**: Every contradiction of a paid payment raises an operational signal — 100% — and is visible on the order's own record, while routine repeat notifications raise zero signals. The measure is that the two are never confused: no contradiction is lost in retry noise, and no retry is reported as a contradiction.
- **SC-019**: No paid order is ever moved, and no issued ticket is ever invalidated, by anything — automated or human. Payment is one-way in this system's record: a completion may revive an expired order, nothing revokes a completion.
- **SC-020**: Exactly one payment session exists per order — verifiable across the full order history as one gateway transaction per order, with no order carrying a second.
- **SC-021**: The deadline a guest counts down to and the moment their code stops being accepted are the same instant for 100% of orders, with no order relying on a locally computed deadline unless the gateway returned no usable expiry and reported it.
- **SC-022**: A guest refused a resend is told how long to wait, and the button becomes usable again on its own when that time is up — verifiable as a resend accepted on the next press with no reload in between. Zero confirmation screens reach a state where the resend control is disabled with nothing that will ever re-enable it.
- **SC-023**: A single malformed resend request refuses only itself. It changes nothing for any other order: a resend for an unrelated order is accepted in the same window, 100% of the time.
- **SC-024**: Every resend attempt is accounted for in the logs with its real outcome, so an attempt that sent no mail can be told apart from one that was never made — the measure is that no attempt reaches the server without leaving a trace.
- **SC-025**: 100% of callback answers parse as the standard `{code, message, data}` envelope — across acknowledgement, settle refusal, authentication failure, unreadable body, and internal fault — with zero empty bodies and zero bodies outside the envelope.
- **SC-026**: A settle refusal is tellable from an acknowledgement by the envelope code alone, without reading `data` and without a difference in the status line, and its `data` names every ticket type short of covering the order and by how much — so an operator can size the top-up from the response without a database query.
- **SC-027**: Every outcome that raises an operational signal is identifiable from its response alone — 100%, each with its own envelope code — so a caller can tell an unrecognised reference from a withdrawal from a contradiction without reading a log. The uneventful outcomes remain byte-identical to each other, and no signalled anomaly ever shares a code with them.

## Assumptions

- **Callback path**: Settled at `/v1.0/callback/exec` from the gateway's own dispatch code. The `/callbacl/exec` in the original description was a typo, and the `/v1.0` prefix it omitted is mandatory.
- **Callback delivery guarantees**: At-least-once, with a finite *automatic* budget. The gateway retries only on a non-200 or a timeout, at most 3 times, 10 seconds apart, with no dead-letter queue — so a notification lost after that budget is exhausted will not come back **by itself**. It can, however, be asked for: the gateway offers an operator-invoked resend per transaction, which is what makes FR-019's recovery path possible. An earlier version of this assumption said there was no manual redelivery at all; that was inferred from the automatic-retry code rather than observed, and it was wrong.
- **Callback API key**: A single shared key for the whole integration, held by this project and by the gateway. Not per-order, not per-environment-derived, and not tied to the `client_id`/`client_secret` pair used on the outbound call.
- **Payment method scope**: QRIS is the only payment method in scope. The gateway contract supports virtual account, e-wallet, debit card, credit card, crypto, bank transfer, and cash; none of those are part of this migration.
- **Currency**: All amounts are Indonesian Rupiah, matching the current system.
- **Amount**: The amount sent is the order's total payable including all fees — the same figure the guest is shown, and the same figure the code encodes. The specific shape in use today is one percentage fee (PPN) and one flat fee (Admin Fee), but the underlying model is general: any number of active fee rows, each either a percentage of the subtotal or a flat amount, ordered by position. The stated formula is that model's current instance, not a narrowing of it.
- **Reference identifier**: The reference sent to the gateway is the order number, unchanged and unsuffixed. Any future change to the order-number format has to respect the gateway's 19-of-25-character budget.
- **Code refresh withdrawn**: An earlier feature refreshed the code partway through the payment window. Its mechanism — a suffixed reference per attempt — existed because the previous provider treated its reference as unique per transaction and would not issue a second code against the same one. Neither the mechanism nor the need survives here: the gateway now returns the code's own expiry, so the deadline and the code's lifetime are the same instant by construction, and a mid-window replacement has nothing to correct. Removing it retires the refresh endpoint, the per-attempt suffix and the suffix-stripping that matched it back, the re-issue counter and its payment-log marker, and the client refresh timer and the interval served to drive it.
- **Deadline ownership**: The gateway alone decides the payment window. Nothing is requested; the expiry it returns (`qr_ea`) is adopted as the order's deadline whatever its length. The existing server configuration (15 minutes by default) survives in two narrower roles: the basis for the FR-009b fallback when no usable expiry comes back, and the expectation FR-009d compares against to notice a window that has silently changed. It is no longer a request, and no longer a decision.
- **Payer name**: Not among the gateway's required fields, but sent when known — it is what lets support match a payer to an order on the gateway's dashboard, which is the evidence User Story 6 depends on.
- **Credentials**: The `client_id`/`client_secret` pair is a protocol formality — the gateway checks it is present but grants nothing on the strength of it. It is configured rather than hardcoded anyway, which costs nothing and means no code change is needed if the gateway later begins enforcing it. The one genuine secret is the inbound callback API key.
- **No environment self-declaration**: Dropping the environment selector means the address is the only thing saying where the system points, so no two settings can contradict each other. The trade is that nothing can recognise a *stale* address: a deployment carrying a development endpoint into production starts cleanly and takes real orders. Deployment tooling, not this system, is where that has to be caught.
- **No schema change for configuration**: This feature adds no table, column, or migration for reaching the gateway. The original request was for the address to live in the database; that was reversed deliberately in favour of the existing environment-configuration mechanism, which every other external dependency already uses. The cost is that switching gateway environments needs a restart rather than a row update — accepted.
- **Merchant account number**: Absent from the sample request, so treated as optional and not sent.
- **Amount verification**: The notification carries no amount, so verifying that the amount paid matches the amount owed is not possible from the notification alone and is out of scope for this feature.
- **Transaction date**: The date the gateway reports is treated as informational. Ordering and idempotency decisions rely on the system's own records, not on a value supplied by the caller.
- **Transaction type**: Only deposits are expected on this endpoint; withdrawals are refused (FR-020).
- **Provider retirement**: No dual-running. The previous provider is not selectable once this ships; whether its adapter code is deleted or left dormant behind the gateway abstraction is a planning-phase decision, not a behavioural requirement.
- **In-flight orders**: Unpaid orders created against the previous provider before the switch are allowed to expire naturally. No payment data is migrated and no back-compatible notification path is maintained for them.
- **No outbound status query**: The gateway abstraction loses its "fetch the provider's status" capability, and with it the guest-facing status-check route. Recovery moves from an automated provider round-trip to the operator-invoked resend in User Story 6. This is a reduction in *automated* recovery, accepted because the capability does not exist to build on — but not a reduction in recovery itself, since the resend delivers the same status through the same path.
- **Recovery trusts nobody's word**: the operator's judgement decides whether to *request* a resend; the gateway alone decides whether a payment happened. Nothing in this system records a payment on a person's say-so (FR-022d), so there is no operator action whose only control is an audit trail. What ops does inside this system — look an order up, top up quota — is reversible and visible; what settles the order is the gateway.
- **Unchanged surfaces**: Booking, quota holds, ticket issuance, and ticket delivery are unchanged. The guest payment page changes per User Story 5; the admin area gains two read-only views in User Story 6 (an order's notification history and what it holds); the live status channel changes per FR-021d–i.
- **Status delivery supersedes a previous decision**: an earlier feature made interval polling the standing fallback beneath the live stream, chosen deliberately to stay correct behind intermediaries that buffer streaming responses. That rationale still holds, so the polling path is narrowed rather than deleted: it no longer runs alongside a healthy stream, and it engages only when the stream is known to have failed — including the silent case the original decision was made for, which FR-021e is what makes detectable.
- **The order read endpoint stays**: "remove polling" means removing the fixed interval that runs beside a healthy stream, not the endpoint. The page still needs it for the initial render, for the refresh the stream triggers, and for the FR-021f fallback.
- **Withdrawn (spec 020) — derive the QRIS frame's merchant identity from the code** instead of configuring it. There is no longer a displayed identity to derive, so this is not deferred work but closed work. The original entry follows for the record.
  > *Deferred — derive the QRIS frame's merchant identity from the code* instead of configuring it. Everything the frame displays is already encoded in the payload: the merchant name, the city, the registration number, and the terminal label. Parsing it would make the displayed identity provably the same one the payer's app shows, and would retire FR-021b's manual re-verification and its matching edge case. Fixed labels are acceptable while one merchant account serves one event brand; they stop being acceptable the moment a second account, a second brand, or a white-labelled event appears.
- **Deferred — ask the gateway for a call that returns an existing code by reference.** A duplicate-reference error proves a code exists while giving no way to reach it, which is the only thing that turns a lost response into an unrecoverable checkout. One read call would make that state fully recoverable. Worth raising with the gateway team as a contract request rather than engineering around.
- **Accepted — a redelivered notification may settle an order of any age.** Nothing reads the order's age or the event's date, so a resend requested long after the event would still settle the order, take the seats, and email tickets to a show that already happened. The operator is a person who has just examined the order and chosen to resend it, so the guard would be catching their mistake rather than the system's, and the realistic gap between a customer complaint and a resend is hours. Recorded rather than built; refusing past the event date is a small change if it ever bites.
- **Deferred — detect paid-but-expired orders proactively.** With no status query and a ~30-second retry budget, the first signal that a callback was lost is currently a customer complaint. An alert on the mismatch, or a periodic comparison against the gateway's settlement report, would find them first.

## Dependencies

- The shared payment contract module (`cdtc/go`) is available as a private dependency and is already declared in the backend build; access requires the private-module credentials described in `PRIVATE_MODULE_SETUP.md`. **The version pinned in the build predates the QR expiry field and must be advanced before FR-009 can be satisfied** — decoding against the older shape drops the expiry silently rather than failing. A version carrying the field is published; the exact one to pin is named in the plan's research.
- The Manjo gateway team must supply the endpoint address for each environment and the merchant network account number and `client_id`/`client_secret` credential, and must be configured with the callback API key this project issues.
- A gateway environment (or a stand-in speaking the same contract) must be reachable from the test environment for end-to-end verification.
- Support staff need access to the Manjo gateway's own dashboard and to its per-transaction resend control, since the dashboard is the only evidence a claimed payment can be checked against and the resend is the only thing that can settle the order (User Story 6).
