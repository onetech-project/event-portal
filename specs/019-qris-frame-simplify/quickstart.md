# Quickstart: validating QRIS Frame Simplification

**Feature**: `019-qris-frame-simplify` | **Date**: 2026-08-18 | **Phase**: 1

How to prove this feature works. The order matters: step 2 must be run **before** any
source change and must fail. A green run at step 2 means the rig is not supplying the
retired values and every later green is meaningless.

---

## 0. Prerequisites

The acceptance runner does not own the infrastructure. Bring it up first:

```bash
REDIS_PORT=6380 docker compose up -d postgres redis mailpit
docker compose run --rm migrate up
```

Mailpit is not optional — the delivery specs read real messages off it.

Frontend tooling needs `node` on `PATH`; it is not there by default and `npx` is
intercepted. Prepend this to every frontend command:

```bash
export PATH="$HOME/.nvm/versions/node/v26.5.1/bin:$PATH"
```

`frontend/package.json` defines only `dev`/`build`/`start`/`lint` — there is no `test` or
`typecheck` script, so the local bins are called directly.

---

## 1. Wire the acceptance rig to supply the retired values

Before writing any assertion, give the `frontend` web server in
[`e2e/playwright.config.ts`](../../e2e/playwright.config.ts) the five values the frame is
about to stop reading, alongside the `API_BASE_URL` it already sets. Use the bare runtime
names (they win over any `NEXT_PUBLIC_*` in a developer's gitignored `frontend/.env`) and
values that cannot occur by accident:

```
QRIS_MERCHANT_NAME    = E2E-MERCHANT-MUST-NOT-RENDER
QRIS_MERCHANT_ID      = E2E-NMID-MUST-NOT-RENDER
QRIS_TERMINAL_LABEL   = E2E-TERMINAL-MUST-NOT-RENDER
QRIS_ACQUIRER_CODE    = E2E-ACQUIRER-MUST-NOT-RENDER
QRIS_PRINT_VERSION    = E2E-VERSION-MUST-NOT-RENDER
```

Why this is required, and why the obvious alternative silently fails, is
[research.md D-3](./research.md). In short: `frontend/.env` is gitignored, so without this
block the assertion is red on a developer machine and green in CI *before* the change.

## 2. Red first — the step that must not be skipped

With the rig wired and **`qris-panel.tsx` still unmodified**, add the card-contents
assertion and run only the journey that reaches the payment screen:

```bash
cd e2e && npm test -- guest-purchase --grep "browses, books, pays"
```

**Expected: FAIL.** The failure message must name the strings it found — that is the
proof the frame is genuinely printing them and the assertion is looking in the right
place. Record the failure output; spec SC-005 asks for it.

If this passes, stop. Something is wrong with step 1, and every subsequent green is a
false one.

## 6. Look at it

The acceptance suite proves the five fields are gone. It does not prove the frame looks
right, and FR-006 is a visual requirement.

```bash
cd frontend
export PATH="$HOME/.nvm/versions/node/v26.5.1/bin:$PATH"
npm run dev
```

Drive a real order to the payment screen, then check:

1. **Stacking order** — QRIS and GPN marks *above* "Scan to Pay", not below.
2. **No gap** — nothing conspicuously empty between the marks and the code.
3. **Wedge checkpoints** — at 522 px frame width, the top of the QR, the baseline of
   `SATU QRIS UNTUK SEMUA` and the top edge of the red corner wedge land where the Figma
   render puts them ([research.md D-9](./research.md)).
4. **Narrowest viewport** — the step captions still sit on the red wedge and do not spill
   onto the white. The caption block is sized to the wedge, not to its content; this is
   the failure mode the existing code comment warns about.
5. **Scan it** — with a real QRIS app, or at minimum a QR decoder, confirm the code still
   resolves. FR-008 says the payload is untouched; confirm the rendering did not change
   its size or crispness enough to matter.

Then, with `endedStatus` exercised (let a hold expire, or cancel an order through the
admin console):

6. The frame is still there, the code is replaced by the explanation, the total reads
   "Order total", and none of the five fields have returned.
